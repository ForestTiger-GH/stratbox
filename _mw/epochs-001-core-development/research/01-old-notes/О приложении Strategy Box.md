# 1. Лаунчер

Лаунчер — это отдельное desktop-приложение, распространяемое как Stratbox Launcher.exe. Его задача — не содержать внутри всю логику stratbox, а быть стабильным загрузчиком и точкой входа для пользователя. Он должен запускаться одной кнопкой, без ручной настройки Git, Python, путей или версий со стороны коллег.

При запуске лаунчер открывает небольшое центральное окно-заставку в стиле офисных приложений: логотип, название, краткое описание, строки статуса и индикатор прогресса. Это окно показывает ход старта: проверку среды, поиск или создание конфигурации, загрузку или обновление репозитория, подготовку Python-окружения, загрузку интерфейса. Тяжёлые действия выполняются в отдельном рабочем потоке, чтобы окно не зависало и не выглядело “мертвым”.

На первом запуске лаунчер определяет рабочую папку приложения. По умолчанию путь должен подставляться автоматически, без лишних вопросов пользователю. Базовый рекомендуемый вариант — локальная папка пользователя, например C:\Users\<user>\Stratbox. Возможность изменить путь должна оставаться, но как необязательное действие через отдельную кнопку или небольшое окно выбора каталога. Program Files использовать не следует: это создаёт лишние проблемы с правами, автообновлением и записью служебных файлов.

Путь установки и минимальные настройки лаунчера не хранятся внутри EXE. Они сохраняются в локальном конфиге пользователя, например в %LOCALAPPDATA%\Stratbox\config\launcher.json. В этом конфиге фиксируются путь установки, путь к репозиторию, путь к виртуальному окружению, рабочая ветка, режим автообновления, поведение при закрытии окна и выбранный профиль данных. Это позволяет сделать первый запуск полностью автоматическим и не требовать от пользователя повторной настройки.

После определения путей лаунчер создаёт рабочую структуру приложения: папку с репозиторием, отдельную папку под venv, каталоги логов, runtime и cache. Далее он либо клонирует stratbox, либо обновляет уже существующий локальный репозиторий. Основной сценарий — автообновление рабочей ветки stable при каждом запуске. Если обновление не удалось, приложение не должно останавливаться: оно должно явно сообщить, что используется последняя локальная версия, и продолжить работу.

Лаунчер также отвечает за подготовку окружения. Он создаёт и обслуживает локальный .venv, устанавливает или обновляет зависимости и после этого запускает основной интерфейс из самого репозитория. Таким образом, EXE остаётся небольшим и редко меняется, а основное приложение и бизнес-логика обновляются из GitHub автоматически.

В основном окне приложения должна быть доступна кнопка Обновить репозиторий. Она вручную запускает тот же цикл обновления: проверка Git, fetch/pull, обновление зависимостей, запись в лог, показ текущего коммита и времени последнего обновления. Если в результате обновления изменилась логика интерфейса, приложение должно предлагать перезапуск для применения новой версии.

Лаунчер должен поддерживать работу через системный трей. Закрытие окна по кнопке X не завершает процесс, а скрывает его в область уведомлений. Из трея пользователь должен иметь возможность открыть интерфейс, обновить репозиторий, открыть журнал и завершить приложение полностью. При этом сам процесс должен быть один: повторный запуск EXE должен либо фокусировать уже открытый экземпляр, либо уведомлять пользователя, что приложение уже работает.

Итоговая роль лаунчера: стартовое окно, первичная конфигурация, хранение локального bootstrap-конфига, установка и обновление репозитория, подготовка окружения, запуск основного GUI, управление жизненным циклом приложения и базовые сервисные действия.

# 2. Интерфейс, работающий из stratbox

Основной интерфейс живёт не внутри EXE, а внутри обновляемого репозитория stratbox. Это уже не просто оболочка над отдельными скриптами, а пользовательский слой приложения, запускаемый лаунчером после подготовки среды. Такой подход разделяет обязанности: EXE отвечает за загрузку и запуск, а stratbox — за прикладной GUI, задачи, профили файловой среды и дальнейшее расширение функциональности.

Интерфейс должен загружаться из локальной копии репозитория и опираться на конфиги задач и профилей, лежащие рядом с кодом. Это позволяет менять сценарии, кнопки, описания, параметры и структуру интерфейса обычным обновлением GitHub, без пересборки EXE. Сам интерфейс должен быть аккуратным, Windows-подобным, с собственным логотипом, иконками кнопок, понятными блоками параметров, ссылками на источники и каталогами результатов.

В интерфейсе должен быть реализован слой задач. Пользователь выбирает сценарий, видит его описание, параметры запуска, каталоги входа и выхода, ссылки на источники данных и кнопки запуска. Основные действия: ручной запуск сценариев, открытие папок на диске, открытие источников в браузере, просмотр журнала выполнения, проверка среды. Интерфейс не должен содержать в себе предметную бизнес-логику; он должен собирать параметры и запускать готовые модули stratbox.

Ключевым архитектурным элементом становится FileStore. stratbox не должен жёстко зависеть от конкретного физического местоположения данных. Он должен работать через абстракцию файловой среды, а интерфейс и профили должны определять, какой корень использовать в текущей сессии. На первом этапе это может быть обычный локальный LocalFileStore, направленный либо на W:\, либо на локальный каталог на диске C:. Внешний NetDrive в этом случае рассматривается как смонтированный локальный диск, а не как отдельный файловый транспорт. Это позволяет использовать одну и ту же доменную логику и для внешнего хранилища, и для локальной копии каталогов.

Интерфейс должен поддерживать профили среды. Базовые профили: NetDrive W: как основное внешнее хранилище, локальная папка на C: для автономной работы и будущий профиль под домашний мини-сервер. Переключение профиля должно менять корневой путь FileStore без изменения прикладного кода. Профиль также должен проходить проверку доступности: существование корня, доступность чтения и записи, наличие ключевых каталогов. Выбранный профиль сохраняется в пользовательском конфиге.

Интерфейс должен показывать информацию о текущей установленной версии приложения: ветку, коммит, путь до локального репозитория, путь до данных, время последнего обновления, активный профиль среды. Также в нём должны быть сервисные кнопки: открыть папку кода, открыть папку данных, открыть логи, открыть GitHub, проверить среду. Это повышает прозрачность и делает приложение понятным для пользователя и сопровождающего.

Отдельный задел должен быть оставлен под фоновый мониторинг источников. Логика проверки ЦБ, Росстата и других внешних источников должна размещаться в stratbox как обычные модули и функции, пригодные для ручного запуска, запуска по расписанию и будущей интеграции с внутренним scheduler/Apache Airflow-подобной системой. Интерфейс должен уметь запускать такие проверки вручную, показывать их статус и открывать логи, но сам не обязан быть единственным местом исполнения 24/7-задач. Для постоянного расписания лучше закладывать внешний оркестратор: Windows Task Scheduler вне банка и корпоративный scheduler внутри банка.

Структурно stratbox превращается в приложение с отдельным пользовательским слоем. Внутри репозитория должны существовать каталог интерфейса, каталог конфигураций задач и профилей, служебные модули запуска, логирования, работы с путями и профилями, а также ресурсы интерфейса — брендовые изображения, иконка приложения и иконки кнопок. EXE при этом остаётся стабильной дверью в приложение, а сам stratbox — обновляемым функциональным ядром и GUI одновременно.

Итоговая концепция: лаунчер — это bootstrap и управление установкой, обновлением и жизненным циклом приложения; интерфейс из stratbox — это основное desktop-приложение для работы с данными, сценариями, профилями хранения, журналами и будущими мониторинговыми задачами.

# Структура работ

- Этап 1. Архитектурная фиксация
  - Зафиксировать роль Launcher.exe как bootstrap-приложения, а stratbox — как обновляемого основного приложения.
  - Зафиксировать разделение на два слоя: лаунчер и GUI/логика внутри репозитория.
  - Утвердить базовую схему каталогов: repo, venv, logs, runtime, cache, пользовательский конфиг.
  - Утвердить рабочую ветку для пользователей (stable) и ветку разработки (main).
- Этап 2. Профили среды и FileStore
  - Определить модель профилей данных: NetDrive W:, локальный каталог на C:, будущий домашний сервер.
  - Привязать профили к FileStore без жёсткой прошивки путей в доменный код.
  - Описать формат конфигов профилей и механизм выбора активного профиля.
  - Реализовать базовую диагностику профиля: доступность корня, чтение, запись, наличие ключевых каталогов.
- Этап 3. Bootstrap-конфигурация
  - Определить место хранения локального bootstrap-конфига пользователя.
  - Зафиксировать состав конфига: путь установки, путь к repo, путь к venv, ветка, автообновление, режим сворачивания в трей, выбранный профиль.
  - Продумать сценарий первого запуска без лишних действий пользователя.
  - Определить дефолтный путь установки и необязательный сценарий его изменения.
- Этап 4. Базовый Launcher
  - Сделать минимальный Launcher.exe, который запускается одной кнопкой.
  - Реализовать стартовое окно-заставку с логотипом, прогрессом и строками состояния.
  - Реализовать сценарий первого запуска: создание конфига, создание рабочих каталогов, подготовка среды.
  - Реализовать сценарий повторного запуска: чтение конфига и автоматический старт без вопросов.
- Этап 5. Автоустановка и автообновление репозитория
  - Реализовать клонирование stratbox, если локальной копии ещё нет.
  - Реализовать обновление локального репозитория при каждом старте.
  - Реализовать безопасную работу при недоступности GitHub: запуск на последней локальной версии.
  - Добавить журналирование всех операций обновления.
- Этап 6. Подготовка Python-окружения
  - Реализовать автоматическое создание и обслуживание локального venv.
  - Реализовать установку и обновление зависимостей проекта.
  - Учесть сценарий первого запуска и сценарий обновления зависимостей после изменения репозитория.
  - Добавить проверку корректности среды перед запуском основного GUI.
- Этап 7. Запуск основного приложения из stratbox
  - Настроить запуск GUI не из EXE, а из локальной копии репозитория.
  - Развести bootstrap-часть и основной интерфейс на уровне процессов и модулей.
  - Обеспечить передачу в GUI текущего профиля, путей и состояния среды.
  - Зафиксировать механизм перезапуска приложения после обновления интерфейса.
- Этап 8. Базовый интерфейс внутри stratbox
  - Собрать главное окно приложения.
  - Реализовать блок выбора сценария.
  - Реализовать блок параметров запуска.
  - Реализовать блок статуса среды и версии приложения.
  - Реализовать журнал выполнения и сервисные кнопки.
- Этап 9. Управление задачами
  - Описать формат конфигов задач: название, описание, параметры, модуль запуска, ссылки, каталоги.
  - Реализовать загрузку задач из конфигурации, а не через жёсткую прошивку в GUI.
  - Подключить первые прикладные сценарии: формы ЦБ, архив исходных файлов, другие базовые задачи.
  - Настроить запуск задач через единый механизм вызова модулей stratbox.
- Этап 10. Сервисные действия в интерфейсе
  - Добавить кнопку Обновить репозиторий.
  - Добавить открытие папки кода, папки данных, папки логов.
  - Добавить открытие GitHub и внешних источников.
  - Добавить просмотр текущей ветки, коммита, времени последнего обновления.
  - Добавить проверку рабочей среды по запросу пользователя.
- Этап 11. Трей и жизненный цикл приложения
  - Реализовать сворачивание интерфейса в системный трей вместо полного закрытия.
  - Реализовать меню трея: открыть, обновить репозиторий, открыть лог, выйти.
  - Реализовать защиту от повторного запуска второго экземпляра приложения.
  - Настроить корректное разделение между “скрыть” и “завершить”.
- Этап 12. Визуальная часть
  - Подготовить фирменную иконку приложения.
  - Подготовить набор внутренних иконок для кнопок и статусов.
  - Привести splash-окно и основной GUI к единому стилю.
  - Утвердить структуру хранения графических ресурсов в репозитории.
- Этап 13. Логи, диагностика, отказоустойчивость
  - Разделить логи bootstrap, обновления, среды и запуска задач.
  - Продумать человекочитаемые сообщения об ошибках.
  - Реализовать мягкое поведение при частичных сбоях: нет сети, нет GitHub, отвалился W:\, не обновились зависимости.
  - Добавить быстрый доступ к логам из интерфейса.
- Этап 14. Watcher-задачи и задел на 24/7
  - Выделить watcher-логику в отдельный слой внутри stratbox.
  - Спроектировать базовые сценарии мониторинга ЦБ, Росстата и других источников.
  - Отделить ручной запуск watcher-задач из GUI от фонового запуска по расписанию.
  - Подготовить хранение состояния watcher-задач и их журналов.
- Этап 15. Интеграция с внешним расписанием
  - Подготовить запуск тех же задач через Windows Task Scheduler вне банка.
  - Подготовить архитектуру для будущего запуска на домашнем мини-сервере.
  - Подготовить код к отдельной интеграции с внутренним scheduler/Airflow-подобной системой внутри банка.
  - Обеспечить единый прикладной код для GUI, планировщика и ручного запуска.
- Этап 16. Упаковка и сопровождение
  - Собрать и стабилизировать Launcher.exe.
  - Описать процедуру распространения среди коллег.
  - Описать процедуру обновления и отката рабочих версий.
  - Подготовить короткую пользовательскую инструкцию и техническую инструкцию сопровождения.
