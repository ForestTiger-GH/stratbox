## 2. Material mismatch discovered in design implementation

The prior documented `LocalOutputPublisher.publish()` computed a digest from `read_closed_staging(staging_ref)`, then asked a separate `read_closed_staging(staging_ref)` for format validation, finally called `finalize(intent, staging_ref, receipt)`. The same pathname was reused with **no proven generation fence**. Another actor or store operation could change staging contents between reads, or before finalization. The sketch's claim about hashing *the bytes subsequently validated and finalized* was stronger than its actual type and algorithm.

**Source-bounded correction:** add a typed `StagingSeal(staging_ref, generation, byte_count, sha256)`, and a port requiring `seal_closed_staging()`, `read_sealed_staging(seal)` and `finalize(intent, seal, verified_receipt)`. Every operation is explicitly bound to the **same backend-enforced generation**, with count/SHA validation of the first read; final observed content must match both digest and size. A mismatch quarantines before physical finalize, and a generation change on finalization yields an explicitly uncertain effect requiring reconciliation. This design imposes a **proof obligation on the actual storage adapter**: a pure name, mtime or two separate path reads cannot satisfy the generation-bound promise. It may need an immutable staging capability/open handle, conditional object-generation commit or an exclusive resource guarantee; these are choices for real target storage review, not assumed current `FileStore` features.
