## H-01 — local Windows width Save fails

**Knowledge-only answer:** On the pinned Windows `PreferencesService`, `save(width=1777)` changes the in-memory `AppUserConfig.window.width` **before** the attempted file save. A synthetic `Path.write_text` fault before disk writes leaves RAM with the new width and `app.json` with the previous width; restart from that unchanged disk restores the old value. In another injected partial-write scenario the old file can instead be truncated/corrupted, so **restart restoring old width is conditional on where the failure occurred**, not a guaranteed recovery mechanism. Neither a visible window resize nor an optimistic preference control proves a durable save. The six distinct roles are proposed input → validation → persistent value → effective policy → surface projection → independently sealed historical Run. A historic Run cannot be rewritten by a width preference (and resizing itself is layout, not a bank calculation). **Current claim** is the pinned synthetic Windows behavior; versioned/atomic persistence and UI warning are **target** safeguards.

**Maintained-only evidence:** `docs/current-how/windows-application.md` §“Executed pinned Settings configuration failure windows”; `docs/science/application-state/settings-policy-preferences-and-drafts.md` §§1–4,7.

**Falsifier:** force a short partially successful write that corrupts `app.json`, not a failure before write: a naïve automatic restart cannot promise previous settings; invalid JSON may raise `AppConfigError`. **Unknown:** real Windows power loss and live Qt repaint outcome.

## H-04 — same publisher bytes, changed decoder and report renderer

**Knowledge-only answer:** Byte SHA equality proves equality of a particular **observed payload** (given real consumed-byte receipts). It does not freeze parser, registry, scope/basis, methodology, validity or renderer. Two Runs can read byte-identical official publications but apply different parser versions, source selection, registry mapping, unit interpretation or method revision; resulting analytical quantities may differ. Even if the computed domain result is identical, a new versioned StyleSet/renderer may present different rounding, scales, separators, missing markers or typography. Distinguish locator/publisher identity, actual byte content, parsed record, semantic comparable observation, calculation result and displayed representation. A displayed `0` might mean rounded small positive or an absent value incorrectly formatted; never infer official publisher revision from render appearance alone. Reproducibility requires the actual *used* bytes/receipt, decoder and methodology/registry revisions, unit/perimeter metadata, selected style/renderer versions and output receipt at the claimed replay tier. No automatic full R4 bitwise replay is shipped.

**Maintained-only evidence:** `docs/science/data-and-knowledge/source-observation-vintages-and-replay.md` §§2–8,12–13; `docs/science/artifacts/atomic-style-set-cross-format-resolution-and-conformance.md` §§2–3,6; `docs/science/artifacts/report-formatting-profiles-metadata-and-evidence.md` §§4–5; `docs/science/data-and-knowledge/observation-semantics-comparability-and-claims.md`.

**Falsifier:** equal consumed SHA with different economic results cannot be explained by the official bytes alone; changing source scope or code is a separate candidate cause. **Unknown:** whether a given renderer change is only display or actually changed the exported numeric cell's machine representation — needs exact artifact evidence.

## H-05 — scheduled occurrence re-evaluated; lost host ACK; file effect possible

**Knowledge-only answer:** The automation *rule*, evaluation, deduplicated occurrence, admitted logical Run, physical Attempt, effect/postcondition, resource claim and notification are different identities. Re-evaluating the same due instant should produce the same occurrence identity under a defined rule revision/civil-time policy, but **does not prove** no prior Run was admitted. Lost host admission ACK is **UNKNOWN** until reconciliation by stable intention/admission key and canonical parameter digest; it is not `REJECTED`. A lost file publish ACK after actual effect might mean **OUTCOME_UNKNOWN** despite a completed write. Do not generate a new invocation identity and blind retry a destructive write. Determine existing host Run, effect generation and current target via authorized receipts, apply CAS/fencing against stale workers, recheck delegated grants/plan approvals at actual effect time. The application authority owns this; existing Windows background descriptors are not a running scheduler, while a GUI disconnect alone cannot define Job outcome.

**Maintained-only evidence:** `docs/science/automation/trigger-occurrence-identity-and-governed-execution.md` §§1–2,4–8; `docs/lcd/automation/trigger-occurrence-and-scheduling-construction.md` §§3–5; `docs/lcd/capabilities/curated-machine-operation-adapter-construction.md` §3; `docs/science/capabilities/machine-discovery-bindings-and-adapters.md` §8; `docs/science/artifacts/output-identity-publication-and-availability.md` §§6–7.

**Falsifier:** two scheduler evaluations and two transport retries with differing intention keys could cause two physical effects even when only one due instant existed. **Unknown:** deployed scheduler/transport transaction and exact DST/overlap policy.

## H-06 — singleton provider conflict, false healthy, official source unavailable

## H-07 — FRG latest-by-name, stale internal target, archived old bytes

**Knowledge-only answer:** The pinned legacy FRG recognizes source families and chooses a latest input largely by filename/period/normalization, which is not proof of official publisher date or file content. The actual current `copy_latest` row **skips** when its target exists and overwrite is disabled. Its ZIP member collection then **prefers that existing target** over the newly chosen source path, without verifying that the target digest matches the selected latest source; the ZIP can therefore be `done` with **stale economic data**. The current artifact/source studies preserve this as a demonstrated *synthetic source-executing* fault case, not a reported installed incident. A candidate sound archive must freeze selected source identity/period/actual digest, require content-same target if reused, verify every bundle member and bytes before publish, stage the archive without deleting old target, and obtain storage generation/finalization receipt. Deletion/rename needs separate plan/approval/source recognition/conditional effects. An archive path exists or `done` action flag is too weak.

**Maintained-only evidence:** `docs/current-how/frg-cleanup-effects.md` §“Source-level refinement and five executed synthetic effect failures”; `docs/science/data-and-knowledge/frg-file-selection-cleanup-and-effects.md` §§1–3; `docs/lcd/application/frg-cleanup-effect-plan-construction.md` §§3–5; `docs/science/artifacts/output-identity-publication-and-availability.md` §§6–7; `docs/lcd/artifacts/local-output-publication-construction.md` §4.
