# Operational workbench versus epistemic navigation: bounded architectural conflict

**Producer reconciliation / NOT A PRODUCT DECISION.** Dated original owners: `SB-SRC-0039` (Windows UX source, frozen `0668c3af7cec9862e638ad1b3f74b8f847404fca`), `SB-SRC-0019` (epistemic target research, `00d738012f9dc85d80f89105c9ad71521097e221`), `SB-SRC-0029` (methodological decomposition, `8eafe0b9c74582d721ce24cdd67d010e6975cda5`), and the later 03/04 research of Work and client semantics.

## Competing UX proposals

| Research strand | Proposed IA | Strength | Risk |
| --- | --- | --- | --- |
| Operations/workbench model | **Work / Explorer / Scenarios / Runs** | Fast access to real tasks, files, capability search and operational status; avoids separate rail item per background/cascade/participant object | Deep knowledge claims, forecast/decision state and assurance may remain buried in inspector; file focus may overweight filesystem locators |
| Epistemic/result model | **Work / Data / Knowledge / Decisions / Artifacts / System** (illustrative, not final) | Makes source identity, observations, findings, qualified reliance and decisions first-class discoverable meanings | Can impose many abstract screens on users who primarily update tables; prefigures Knowledge/Decision engines not present in product; expensive new canonical objects and data governance |
| Present Windows implementation | Explorer / Scenarios / Cascades / Background / Participants / Assignments | Directly observed launch/desktop routes and current prototype semantics | Mixes entities, modes and incidental collaboration scaffolds as equal top-level destinations |
| Context-sensitive task journeys | Home on Work; actions and contextual inspectors route into data/knowledge/effects views when material | Avoids permanently multiplying navigation roots and supports portable mobile layouts | Could hide complex independent Knowledge/Decision work if those become common and need their own global indexes |

## What is really conflicting

This is a dispute about **primary mental model and product maturity**, not whether Knowledge exists scientifically. One can preserve full epistemic qualifications while presenting Work/Explorer/Scenarios/Runs as four initial user destinations, and later surface independent Knowledge/Decisions only if real consumer tasks, current objects, authorization and accessible navigation tests warrant. Equally, a data/research-heavy analyst may need an explicitly discoverable Knowledge graph/view earlier than a routine pipeline operator does.

The target cannot be accepted by counting which study is newer. A user story and study population are required. A future cross-platform UI can retain semantic object/action identity while Windows uses rail/inspector, Web uses routes and Android uses compact task pages. A change in navigation must not transfer Authority from Work/Knowledge owners into the presentation layer.

## Falsifying tests before Product admission

1. Expert analyst can explain why a restored banking observation differs from source publication and navigate to evidence without reading Research archive.
2. Operator can find current running Job, failure stage and artifact within minimal navigation steps without learning epistemic ontology.
3. An Analyst/Decision user can recover the forecast vintage, accepted Decision and original qualified comparison after returning a month later.
4. A pending assignment/approval is actionable and permissioned without requiring a redundant top-level Team root unless workload justifies it.
5. Keyboard-only and high-contrast access remain usable with the final information architecture.
6. Mobile client can carry the same Work/Result/Artifact semantics without copying a desktop-only row of six controls.
