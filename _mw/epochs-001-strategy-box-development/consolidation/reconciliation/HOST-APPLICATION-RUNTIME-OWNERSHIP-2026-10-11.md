## The conflict is architectural, not merely terminological

The earlier automation/AI proposal assigns considerable scheduling, Job execution, credential/policy bridging, model gateway and remote-runtime responsibility to the external managed Node/platform boundary. That proposal is conditional on an external capability and is not evidence of platform implementation. The later full web/self-host study argues for an independently running, **product-owned** application host as the authority for users, workspaces, cases, jobs, events, resource conflicts, application authorization, artifacts and application-level audit, while the external platform manages package installation, Node/service lifecycle, environment handoff and host-level recovery.

These two cannot both be silently treated as an implemented or accepted unique owner for application-level authorization and Job consistency. The most stable conceptual separation, also supported by existing newer scientific synthesis, is:

| Responsibility | Legitimate candidate owner | Requires verification |
| --- | --- | --- |
| Managed environment, product installation, lifecycle, Node identity, process supervision | External management platform | Exact released version/connector interface, evidence from direct owner |
| Bank/macro operations, calculations, source/registry validity | Strategy Box analytical core | Direct current code and core conformance |
| Work/Job/Attempt admission, effect policy, case/event state and product Artifact authorization | Strategy Box application authority, potentially headless host | Explicit Product Decision, one authoritative mutation path and crash/ACL tests |
| Physical execution process or scheduling mechanics | Product-owned worker, platform execution service or integrated adapter | Who owns leases, conflict resolution, idempotency, crash recovery and audit receipts |
| Model inference and protocol bridges | Controlled consumer/adapters; provider placement is conditional | Tool/secret boundaries, real permissions, capability version |
| Windows/Web/Android screens | Their own client presentation owners | Consistency of stable IDs and accessibility, not identical widgets |

A useful **interface-level** compromise is possible: product application authority validates and records a Job, while a managed platform provisions or supervises a physical executor through a versioned adapter. This is one **candidate**, not a claim that either side has already implemented it. The difficult ownership question remains who can atomically claim a Job, revoke an Attempt and decide a previously attempted external effect's outcome after a connection failure.

## Distinguish historical claims, proposals and direct facts

- The pinned Windows `ScenarioCoordinator` is Qt/QThread-based and processes one local scenario at a time. This proves neither product-host persistence nor platform-host durable Job execution.
- The pinned five-file JSON history is recent client state, not proof of a shared application database.
- The current external deployment manifest describes a Windows-local foreground surface. A conceptual host in a platform overview does not prove a running product service.
- The 2026-10-07 proposal's `stratbox-host` and `stratbox-web` names are an organizational hypothesis. They are not already approved repositories or deployable artifacts.

## Competing outcomes for Product Authority

**A. External platform as primary application runtime:** fewer product services if platform provides full application-specific Job/ACL/event authority; downside is coupling bank-product meaning to generic platform life cycle and uncertain platform feature coverage.

**B. Product-owned headless host:** clearer application semantics and multi-client ownership; downside is standalone service/database/auth/backup/worker operational burden.

**C. Product application authority plus managed physical execution adapters:** preserves product semantics and leverages platform lifecycle; downside is distributed reconciliation and unclear partial-failure boundaries unless explicit contract and verification exist.

A documentation choice between A/B/C would be premature. The scientific result is the **required owner distinction and verification criteria**, not a vendor or repo choice.

## Falsification and decision evidence

1. Accept a Job on device A, disconnect all clients, reconcile its verified side effects through device B.
2. Crash between effect application and durable receipt; demonstrate one authoritative adjudicator and explicit `UNKNOWN`.
3. Revoke principal access after scheduling but before execution and after an Artifact is published.
4. Crash/restart the platform supervisor while the product state store remains reachable, and vice versa.
5. Execute simultaneous scheduled and manually submitted Jobs sharing one output, with documented lease/conflict semantics.
6. Check exact supported platform connector versions rather than reading future platform marketing as a present feature.
7. Compare operator effort of an embedded/local host, external host service and platform-managed executor; include backups and updates, not only CPU latency.
