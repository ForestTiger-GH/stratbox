## Core concern and independent distinction

The research advocates a boundary between low-level mechanism, reusable building block, subject service, canonical operation, versioned machine-readable composition, resolved execution plan and actual run. The crucial distinction is **definition is not invocation, resolved plan is not observed run, and a machine-readable contract is not proof that its implementation behaves as declared**.

It compares several outside formalisms: JSON Schema as type/validation precedent; tool protocols as presentation adapters; typed workflow DAGs for dataflow; business process/decision modeling for limited state/decision patterns; planning preconditions and effects; bounded expression languages for guards; provenance entities/activities/actors; and event envelopes for transport. This is **comparative Research**, not certification of one universally complete standard nor approval to install one external framework.

## Semantics worth retaining as scientific challenge

- **Knowledge, capability, artifact, execution:** a source or classifier snapshot is a knowledge input; a capability transforms/produces; a durable artifact is a persisted output; a job/run is actual execution state. A generic registry must respect these distinctions.
- **Serializable control plane versus bulk data plane:** typed metadata can travel via JSON-compatible envelopes while large tabular inputs/outputs remain as DataFrames or separately addressed datasets.
- **Domain-rich results:** source coverage and failures, mathematical evidence and validation/conflict detail should not be squeezed into one `ok` boolean.
- **Reproducibility:** a resolved plan can pin exact input/registry/schema/implementation revisions. Dynamic labels such as `latest` must be resolved under a specified policy to be reproducible.
- **Effects and authority:** a declared operation permission/visibility field is not an authorization decision. Exact preconditions, side-effect classes, cancellation/idempotency scopes and observed effect receipts remain separate.
- **Restricted IR:** an analyzable composition language can limit intrinsic operations and prohibit arbitrary hidden Python execution; richer data-dependent reasoning remains a separately governed implementation.
- **Caching/dedup/compilation:** shared work, historical result reuse and replacement with an optimized implementation have different validity conditions and evidence duties.
- **Lifecycle:** capability admission/revocation, domain object state, and job/run state are different transition systems, not one overloaded status enumeration.

## Material conflict with prior Research

The existing `SB-SRC-0024` study proposes three clear product categories (technical Command, user Scenario and multi-scenario Cascade). This study instead introduces a generic composable machine capability and treats a visible Scenario as a possible product projection, while a Cascade might be represented as a composition. **Neither proposal is an accepted ontology.** The conflict is about ownership and consumer-facing lifecycle: a machine Scheme may be below a durable user Work/Case and may coexist with a distinct named Cascade in the interface. There is no valid shortcut to resolution by document count. Formal product semantics and the minimal actual consumer use cases remain open.

## Current implementation evidence and exclusions

The current core has examples of typed request/result, staged escrow operations, FRG plan/apply and evidence-rich reconstruction, but this study **does not demonstrate a shipped universal CapabilityRegistry, SchemeSpec, typed DAG planner, generated-code admission system, optimized binding compiler, remote execution or cross-platform service**. Its sample IDs, YAML and Python snippets are illustrative schemas only. The underlying findings depend on previously analyzed source and operation research; repetitions do not become independent evidence.

The original discusses a prospective external machine consumer in some sections; this publication records only generic capability discovery, governance and execution assumptions. **No details of restricted environments or private implementations are transferred.**
