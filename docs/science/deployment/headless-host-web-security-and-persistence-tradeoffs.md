# Headless analytical hosts, browser security, and state persistence trade-offs

**Scientific scope.** This article examines when a local analytical desktop application needs a separately running application authority, how browser and remote clients can observe the same Work without becoming its owner, and which persistence, security and deployment models are proportionate. **Status:** research-qualified architectural comparison, **not** an approved host repository, public deployment, API, database product choice, or implemented feature. The directly observed Windows baseline is [stratbox-windows at 959e9c4](https://github.com/ForestTiger-GH/stratbox-windows/tree/959e9c4ce1441124af5111c1e025041714e04d3b).

**Product authority cross-reference (2026-10-12):** Subsequent to the original Research, the owner **accepted and planned** a Strategy Box host in **Web/domain** and **Windows/AppDock-host + separate Windows/AppDock client** deployments; the number of Windows repositories remains open. See [admitted host Target WHAT](../../what/strategy-box/host-deployment-commitment.md). This Science article continues to test hosting/security **alternatives and evidence limitations**, not to undo the newer host commitment or claim an implemented service.

## 1. The actual boundary: a client lifetime is not a Job lifetime

An analytical operation in a foreground Qt process can be useful without a server. The [current Qt coordinator](https://github.com/ForestTiger-GH/stratbox-windows/blob/959e9c4ce1441124af5111c1e025041714e04d3b/src/stratbox_windows/presentation/qt_desktop/scenario_coordinator.py) owns one QThread-backed active Case and rejects another concurrent submission. Its [runtime bootstrap](https://github.com/ForestTiger-GH/stratbox-windows/blob/959e9c4ce1441124af5111c1e025041714e04d3b/src/stratbox_windows/runtime/bootstrap.py) directly imports that Qt coordinator. The [five JSON history projections](https://github.com/ForestTiger-GH/stratbox-windows/blob/959e9c4ce1441124af5111c1e025041714e04d3b/src/stratbox_windows/application/history/persistence.py) persist recent cases, events, artifacts, logs and assignments. Their implementation explicitly disclaims database-grade durability; a failed JSON decode returns an empty list, and writes do not use a coordinated cross-file transaction.

These facts support **local foreground execution**, not claims about detached Jobs, concurrent remote users, automatic restart recovery, a shared transactional history or web authentication. The [pinned installed manifest](https://github.com/ForestTiger-GH/stratbox-windows/blob/959e9c4ce1441124af5111c1e025041714e04d3b/appdock/manifest.json) advertises a Windows-local foreground desktop surface; remote service support cannot be inferred from its presence or artifact declarations.

A truly detached job requires an authority that survives browser-tab shutdown and disconnect, claims work independently of the UI request, records each execution transition durably, reconstitutes state after failure and exposes access-scoped snapshots. A proposed acceptance witness is: submit one Job, close every client, observe server-side progress, reopen through another authorized client, resolve the same immutable Job identity and final verified output, then repeat across a host crash with outcome uncertainty represented rather than silently converted to success.

## 2. Four competing arrangements and their actual cost

| Arrangement | Legitimate benefit | Failure boundary | Appropriate conditions |
| --- | --- | --- | --- |
| In-process desktop executor | Minimal deployment, immediate local access, no server operations | The UI process and Job share fate; single-client state and cancellation limitations | Personal interactive analyses with openly stated foreground-only semantics |
| Desktop with a local companion service | Process independence; durable local Job authority is possible | Extra IPC, installation, upgrade, service recovery and migration work | Local runs must survive GUI closure; no external browser promised yet |
| One product-owned headless application host | Shared Work/Job/Artifact authority, server-side permissions and multi-client projections | Authentication, persistence, worker isolation, backup, migrations and incident response become first-class | Actual remote or web multiuser product need |
| Remote desktop/GUI streaming | Reuses existing Qt UI with minimal product-API design | Inherits GUI/session lifetime, accessibility and filesystem assumptions, weak cross-device semantics | Administrative access or narrowly scoped interim workaround, not a browser product |

A separate repository or service boundary is justified by **independent lifecycle and authoritative state**, not by the word “host”, the existence of Linux, or the desire to draw a new component diagram. Source research proposed distinct host and browser codebases; the organizational boundary remains a Product Decision. No additional source tree should be treated as existing solely because this design appears plausible.

A second disagreement concerns ownership. An external managed platform can provision a Node, install distributions, supervise process uptime, inject permitted environment bindings and route health without thereby becoming the authority for a Strategy Box Work acceptance state, bank result, application permission or artifact publication. Conversely, a product host must not reinvent distribution, machine management or external platform account control. A useful test is: **who may issue and reconcile the final app-level mutation when two clients disagree?** That is the application authority.

## 3. Work identity and client-neutral contracts

Shared identity must be independent of display name, process PID, browser connection and physical path. Distinct identities can include Thread/Work, Run, Job, Attempt, event sequence, artifact version and the actor who actually requested an effect. These distinctions do not force a new table for each concept: their persisted separation is justified when ownership, retry safety, visibility, lifecycle or recovery differs.

The browser should send a typed command against an authoritative resource revision and then read a qualified representation. A suggested **candidate**, not implemented API, is:

```text
command: submit known capability + validated parameters + principal + idempotency key
result: accepted / rejected / input_required / unknown, stable Work and Job refs
read: access-scoped snapshot at sequence N
stream: authorized changes after N, or explicit resynchronization
artifact: opaque ID + permitted actions, never an unverified server path
```

A client-disabled button is not authorization. Each mutation requires current object-level authorization and revision preconditions; each artifact download must recheck visibility. A stable idempotency key constrains *admission duplication* only within a declared retention and backend contract: it does not prove exactly-once execution of uncoordinated external effects. Distinguish client request replay, Job deduplication, Attempt retry, side-effect receipt and domain acceptance.

## 4. HTTP and event transport: why simple may be stronger

Ordinary command/response HTTP plus server-to-client event streaming fits the dominant traffic: Job admission and cancel are occasional mutations; progress, messages and completion are server-originated observations. [Server-sent events](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events) provide event IDs and automatic reconnect semantics in browsers. But an event ID or `Last-Event-ID` alone does not guarantee lossless replay, valid authorization after rights change, infinite retention or ordered multi-tenant delivery.

A robust consumer route is **authorized snapshot at sequence N → filtered event subscription after N → detect cursor expiration, authorization change or missing sequence → obtain a fresh scoped snapshot**. The server must define ordering scope: a globally increasing internal sequence need not disclose activity by other users. A filtered, opaque cursor may be safer than exposing global event counts; links to events should be reauthorized after access revocation.

WebSocket is valuable for genuinely bidirectional low-latency collaboration or a terminal-like interactive stream. For status and occasional mutations it adds connection authentication, reauthentication, reconnect, backpressure and protocol complexity without proving better consistency. Similarly, browser offline state is a *possibly stale projection*. Show the last authorized snapshot as stale and restrict shared mutations until connectivity and authorization recover rather than silently merging writes.

## 5. Authentication is not authorization

For a separately published browser host, an authenticated session must be enforced for every sensitive resource and state change. An OIDC identity provider can establish **who** has logged in; Strategy Box separately decides what that principal may do with a specific Work, Node, dataset, log or artifact. Local-account management is a competing air-gapped profile and creates its own password bootstrap, MFA, recovery and audit burden.

For a first-party sensitive browser interface a server-side **backend-for-frontend** session is a defensible default: access/refresh tokens remain on the server; the browser holds a short-lived opaque session cookie with `HttpOnly`, `Secure` and an appropriate `SameSite` policy. The [OAuth 2.0 for Browser-Based Applications BCP, RFC 10017](https://www.rfc-editor.org/rfc/rfc10017.html) distinguishes BFF, token-mediating and browser-only OAuth architectures, with different threat trade-offs; it is not evidence that any one implementation is already shipped. Cookies still require CSRF controls on mutations, trusted origins, careful proxy headers and session invalidation. TLS, authorization tests, upload and error protections remain mandatory.

External exposure should fail closed if authentication, public-origin validation or TLS-edge policy is absent. Reverse proxy, certificate management and allowlisted forwarded headers are *deployment responsibilities*; any claim that an external platform supplies them is conditional on a specific implemented contract. A private loopback development profile has a materially smaller exposure surface than a LAN or public hostname.

## 6. SQL profile debate and storage authority

The concrete requirement is durable, transactional application metadata: principal/session bindings, Work and Job admission, Attempts/leases, accepted events, approvals, read receipts, artifact references and recovery markers. Large Excel/PDF/CSV/ZIP objects and large operation logs have distinct byte-storage, retention and scanning concerns. Putting both in one database merely to have one file is not a semantic requirement.

| Model | Strength | Important limitation |
| --- | --- | --- |
| Existing JSON projections | Transparent, easy prototype inspection | Malformed-file ambiguity, no multi-file atomic transaction, no concurrent claiming |
| Host-local SQLite behind a single authoritative service | Embedded deployment, ACID transactions, minimal infrastructure | Must consider writer contention, backups, host-local file ownership and process topology |
| Host-managed PostgreSQL | Multi-process write concurrency, operational tooling and mature transactional service boundary | Installation, upgrades, administration, resource consumption and backup coordination |
| Database file directly mounted by remote clients | Apparent convenience | Network filesystems can violate locking/latency assumptions and bypass application authorization |

The [SQLite network-filesystem guidance](https://www.sqlite.org/useovernet.html) describes hazards of shared database access over a network filesystem; [SQLite's appropriate uses guidance](https://www.sqlite.org/whentouse.html) supports embedded/single-host designs. Choosing PostgreSQL merely because the client is a browser is an **over-strong inference**: workload, writer topology, availability and administration determine the appropriate engine. Both are candidates; their observed transaction behavior and restore drills matter more than name recognition.

Use one application-facing state contract even if multiple implementation profiles are eventually authorized. Avoid silently divergent consistency semantics between embedded and managed deployments. Durable Job claims need tested lease expiry, fencing against old workers, interruption recovery and a distinction between **outcome unknown** and **definitely failed**.

## 7. File rooms and artifact identity

A single unrestricted shared folder leaks personal uploads; a fully personal folder scheme duplicates common official datasets and inhibits collaboration. The research proposed four logical scopes, which may be implemented using different physical backends:

| Scope | Purpose | Default safety concern |
| --- | --- | --- |
| Shared/node | Approved common inputs, datasets, published results | Group visibility, conflict, publication rights |
| Personal | Drafts, uploads, private analyses | Per-user ACL and separation from global indexing |
| Run | Temporary work, partial exports, staging and provenance | Cleanup, cancellation and partial-publication controls |
| System | Internal state, caches, service logs and secrets references | Never a public Explorer root |

The client refers to `FileRef`, `WorkspaceRef` or `ArtifactRef`; the host validates the authorized scope then resolves a physical storage backend. Free-form absolute server paths, directory traversal (`..`), symlink escape and unauthenticated static `/workspace` mounting are separate threats. Uploads require content validation beyond filename and `Content-Type`, size/decompression limits and untrusted-parser isolation. Previewing active content inside the logged-in web origin can create an XSS boundary; sanitize or isolate previews, and fall back to download where safe rendering is unavailable.

A temporary output, a successful calculation, a readable file and a **published Artifact** are four different states. Publication should validate content, hash and metadata, reconcile the storage move and catalog transaction, and preserve orphan cleanup evidence. Host restart must not declare a partially written document published simply because a filename exists.

## 8. Reliability, backup and security failures

| Failure | Correctly scoped behavior | Disallowed inference |
| --- | --- | --- |
| Browser closes after submit | A detached accepted Job continues where supported | Every foreground Qt Job survives client closure |
| Worker crashes during effect | Record Attempt loss; reconcile effect receipt and source state | Unknown effect means safe automatic retry |
| Database temporarily unavailable | Node/application degraded; protect confirmed state | Empty history means nothing happened |
| Artifact metadata commit fails after bytes appear | Unpublished/orphaned bytes are reconciled | Output exists, therefore visible and accepted |
| Event stream loses cursor or permission | New authorized snapshot, with gap visible | Timestamp sorting reconstructs all events |
| Restore from split DB/byte-store backups | Reconcile generation IDs, hashes and manifests before unfreezing | Separately successful backups form one consistent snapshot |
| Shared upload contains malicious archive | Quarantine and bounded expansion/scan/parse | Extension or MIME header guarantees safety |
| Permission changes mid-stream | Reauthorize reads, revoke active streams if necessary | Login at subscription start authorizes indefinite access |

Health needs separate process liveness, application readiness and degraded component status. Logs for requests and effects require correlation IDs but should redact credentials, raw session tokens, sensitive parameters and unneeded contents. Security audit of rights changes is distinct from user-facing event cards and debugging traces. Retention differs for long-lived case conclusions, medium-lived logs and short-lived worker scratch/presence.

## 9. Operational simplicity is a testable quality, not an aesthetic slogan

An ASGI-like Python host with isolated workers is one plausible integration with Python analytical core. Choosing a particular web framework, proxy, broker, container or orchestration suite before an acceptance profile creates deployment cost without increasing semantic correctness. A single-node durable-job table and leases may suffice before a message broker; high worker count, independent services or cross-node demands may justify a broker later. A container is a delivery method, not evidence of application isolation or transactional effects.

Useful falsification tests: (1) disconnect and reconnect during fast events; (2) crash between external effect and receipt persistence; (3) revoke artifact permissions while its preview is open; (4) two clients race to cancel a job and edit an assignment; (5) run disk-full, DB corruption and restore mismatch; (6) attempt traversal, symlink escape, CSRF and malicious archive upload; (7) measure CPU/memory and administrative footprint at one-user and multiuser loads. Reference checklists such as [OWASP ASVS](https://owasp.org/projects/asvs) are control frameworks, not substitutes for threat-specific execution tests.

## 10. What remains unresolved

**Observed:** only a local foreground Windows surface and an independently importable core are evidenced by the pinned implementation. **Research-supported rationale:** a separately living product application authority allows detached Jobs, multiuser history and remote clients to share one responsible truth owner. **Subsequent direct Product Decision `PD-SB-HOST-2026-10-12-01`: a Strategy Box host is NECESSARY and PLANNED** in both a Web/domain host with browser/Windows/Android consumers and a Windows/AppDock host installation attached to by a distinct Windows/AppDock client installation. **Still undecided:** physical one-or-two Windows repositories, exact host service/process, whether every local desktop is host-backed, database choice, identity/browser exposure policy, durable/recovery guarantees, user file scopes and backup retention. The research rationale did not itself authorize any endpoint or decide a platform package. **Negative conclusion:** remote desktop is not equivalent to a browser product; a public web interface, BFF session, OIDC, SSE and PostgreSQL are not proven merely by describing them.

## 11. Web-exposure boundary: mutations, origin policy, extensions and disconnected clients

**Source status:** pinned [2026-10-07 original Web/self-hosted Research](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md) proposed browser/host controls in §§16–29, 34–38, 77–92, 100–125, 129–135. These are **conditional Research considerations for an actually admitted browser-accessible deployment**, not implemented product endpoints, required new repositories, or approved security policies. The current pinned Windows application is locally Qt-coordinated; the core remains independently importable.

### Four independent trust boundaries and counterexamples

| Boundary | Source-grounded mechanism and alternative | Counterexample or cost |
| --- | --- | --- |
| Browser and session | A same-origin first-party browser *could* use server-held sessions with Secure, HttpOnly, appropriate SameSite, rotation and revocation, and perhaps OIDC Code + PKCE. Standalone local accounts would need separate password/bootstrap/MFA controls. | TLS and an opaque cookie do not by themselves prevent CSRF. SameSite, an anti-CSRF check, Origin/Fetch Metadata policy and avoiding state mutation via GET address different risks. A valid login cannot authorize every object. |
| Browser origin and app endpoints | One trusted static/API origin reduces CORS and cookie complexity. Browser-facing services need threat-specific CSP, HSTS, no-sniff, frame restrictions, trusted Host/origin and explicit reverse-proxy forwarding boundaries. | Permissive Host or untrusted forwarding headers may corrupt security or URL trust. CSP cannot substitute for correct escaping, real authorization or isolation of active HTML previews. A separate trusted frontend origin remains possible but needs additional testing. |
| Client, jobs, artifacts and sources | In a hypothetical host profile, browser submits an authorized command and receives a Case/Job reference. Downloads, previews and official-source input collection are mediated by accountable server-side capabilities. | File existence is not completed Artifact publication; visible cards do not imply permission to read bytes. Browser-direct statistical downloads change CORS, credentials, gateway, caching and provenance assumptions. |
| Extension and active first-party code | Declarative scenario/form/style/settings metadata and safe render hints offer a less privileged extension mode than arbitrary third-party JavaScript in an authenticated Web origin. | A server extension or signed UI bundle does not automatically gain permission to execute scripts, inspect session state or bypass object authorization. Full frontend extension loading requires separately admitted trust, capabilities, CSP/lifecycle and isolation tests. |

The [original API §§16–20](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L465-L575) distinguishes authorization to mutate (principal, object, parameters, current revision, resource limits) from request retry handling. A stable idempotency key can avoid *duplicate admission* within its actual validity window; it cannot unmake an external effect with uncertain outcome. Mutable shared objects need expected revision/conditional update, not unannounced last-write-wins. A safe user-facing error with correlation ID is different from a raw exception in restricted technical logs. Endpoint shapes in original Research are **illustrations**, never evidence of a shipped HTTP API.

### Client lifetime, settings scopes and audit

The [original Web interface §§100–103](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L1887-L1953) distinguishes client connection from accepted server Job life. In an actual persistent-host profile, a disconnected browser may display the last snapshot **explicitly marked stale**, reject shared mutations until reauthorization and recover by authorized snapshot/delta after reconnect. This does not require offline-first collaborative editing. Browser deep links and download/preview actions differ from the Qt desktop's native file open/reveal, so a generic server Scenario creates a Result/Artifact and leaves local opening behavior to the surface.

Five historical [settings scopes §77–82](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L1517-L1647) carry different authority: deployment/system (endpoint, TLS trust, secrets, runtime and storage), node (retention, background policies and quotas), workspace, user (theme, notification and artifact formatting preferences), and device/browser (ephemeral drafts and panel state). A device preference store must not silently hold access/refresh tokens, credentials, secret parameters or private documents. These are candidate scopes, not mandatory settings tabs. Related [settings Science](../application-state/settings-policy-preferences-and-drafts.md) maintains the broader policy distinction.

A browser-enabled system would add HTTP, authorization, session, upload/download and rate-limit observability to the existing core/Case/Job diagnostics, with request, principal, Case/Job, artifact and problem correlation **without raw tokens or full request bodies**. Security audit of permissions, approvals, publication, destructive changes and restoration has separate audience and retention from ordinary debug logging. One user-facing node incident does not entitle every connected user to a technical stack trace; see [safe shared conditions](../collaboration/shared-conditions-and-log-access.md).

The [original threat model §§83–92](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L1650-L1772) also separates account takeover, broken object authorization, script/HTML preview, malicious archive parsing, path escapes, and resource exhaustion. Authentication alone cannot prevent one authorized actor from exhausting a shared node. Quotas, bounded decompression/uploads, worker CPU/memory/time policies, safe parsers and cancellable admission depend on a named operational profile and real risk, not a generic Web checkbox.

### Deployment and contract proportionality

The [original §§108–113 and §§120–125](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L2012-L2290) sketch four **possible** profiles: local Windows (possibly local application host), browser self-host, remote Windows, and Android companion/client. They are proposals, not actual deployed modes. Multiple release cycles could make a versioned API handshake and generated typed clients valuable **without** establishing a backward-compatibility obligation for existing Python APIs. Similarly, a single-node database-backed Jobs/leases/events manager may be sufficient before a broker; Redis/RabbitMQ/Kafka and containerization add costs justified by real worker distribution or operational needs. Application-level Job/rights/Artifact meaning differs from external platform installation/health/storage handoff. Neither a new physical host repo nor a host-first runtime model has yet been admitted as a Product Decision.

The [original §§129–135](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L2331-L2438) additionally proposes showing a planned Scenario's downloads, outputs, destructive actions, resource conflict and required approval before admission. A background or AI actor would have its own principal and bounded capability envelope, **not** silently inherit the last interactive user's rights. Source downloading and source-policy enforcement for a remotely accessed operation would be host/core-side, leaving browser to display safe progress and results. All proposals remain conditional on an authorized real execution profile.

## Original Web-host research: conditional health, sensitivity and lifespan models

Example route names `/livez` and `/readyz` were source-proposed; no implemented Strategy Box or AppDock contract is established by their presence in Research. The scientific necessity is a clear authority-specific disclosure/retention rule: a shared incident may warrant a safe notice while the raw exception, tokens and private paths remain restricted; user preferences cannot override mandatory security retention by changing an ordinary theme/settings toggle.

### Liveness is not readiness, and readiness is not a banking result

Original [§§98–99](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L1849-L1886) distinguishes process-alive from able-to-serve. `/livez` and `/readyz` are **illustrative research path names**, not adopted actual API endpoints. A process may answer a probe while the host fails to admit work because its application state database, configured workspace, analytical runtime/core imports, worker engine, migration state or required identity binding is unready. Conversely, one optional data source's outage may degrade only dependent workflows; unrelated read-only status requests may remain reliable. A single HTTP 200, AppDock launcher PID or process heartbeat certifies neither a running accepted Job nor truthful Artifact publication.

A conceptual health view separates (a) process alive; (b) application ready for a particular command profile; (c) component degraded/unavailable; (d) already accepted Run/effect truth. It should reflect the **actual user capability affected**, rather than advertise one permanent green badge after startup. The same checks apply when Windows/AppDock launches an ordinary service process: a successful launch handshake does not prove the service listener accepts the second Windows client, user identity or worker Job. Any platform health projection follows versioned verified contracts, while Strategy Box owns application-specific readiness and domain outcomes.

### Logical convergence need not prematurely impose identical physical desktop architecture

[§§126–128](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L2293-L2330) warn that permanently separate Windows local JSON/Qt execution semantics and Web transactional host execution would create incompatible Case/Artifact/effect truth. The research proposes *eventual semantic convergence*, possibly one locally launched host serving Windows and a remotely reachable host serving other clients. It explicitly recognizes an interim dual local-versus-remote execution adapter as a candidate.

The later Product Decision **accepts** host capability and both Web/domain and Windows/AppDock host + separate Windows/AppDock client arrangements. It does **not** settle whether every standalone Windows-only user must run an embedded host, how long a local-only executor remains available, whether a host ships in the existing Windows repo or a distinct one, or the state import protocol. Those are engineering and Product choices requiring representative native deployment costs and evidence. Shared **semantics** of admitted Jobs and permissioned Artifacts may be implemented via a common application package and selected adapters; semantic unity does not force a single process, one Qt surface or a central database for all private personal work.

An old local `success` record, absolute file path or `unread` Boolean cannot silently turn into verified host execution, remote Artifact or other users' read cursors. Import should preserve source-version/historical status and observed evidence; a declined import can be correct. Direct notebook access to the Python analytical core remains independent of any host lifecycle.

### Original Web-host MVP acceptance requirements are proposed test candidates, not shipped features

[§§137–143](https://github.com/ForestTiger-GH/stratbox/blob/8459dc58922b7e8df853cf1d9e8131fa9e132580/_mw/epochs-001-strategy-box-development/research/02-base-study/stratbox_web_self_hosted_architecture_research_2026-10-07.md#L2461-L2525) contain source-proposed **separate** acceptance classes. Preserve their actual scope rather than paraphrasing everything as “host ready”:

| Original class | What an engineering verifier would need to observe | Failing shortcut |
| --- | --- | --- |
| Deployment and exposure | Headless service installation without Windows GUI; controlled HTTPS domain/reverse proxy; no unauthenticated external listener; observable readiness | A browser `url` launcher successfully opening a tab |
| Authentication/session | Approved login, explicit logout invalidation, access revocation, safe cookie/session policy and limited security events | A displayed username or permanent browser token |
| Authorization | Viewer/analyst roles, Case cancellation by actual owner/grant, personal Artifact isolation, shared-resource ACL and separate technical-log access | A disabled UI button or permission-sounding capability label |
| Execution lifetime | Accepted stable Run/Job receipt, browser disconnect/reconnect, dedupe, cooperative cancellation, truthful crash/unknown and effect reconciliation | A spawned PID or a client still showing `running` |
| Event delivery | Access-scoped snapshot + live stream with gap/reconnect handling; personal read cursors | SSE alone without exact replay/rights proof |
| Files and workspaces | Shared/personal/run scopes, upload limits, traversal/symlink tests, permissioned downloads, no raw server paths or unguarded static workspace | Path names treated as access tokens or server Data root exposed as a web directory |
| Durability and recovery | Transactional metadata, compatible restore of state+bytes, migration, restart, disk-full and verified Artifact publication fault tests | Database selection, a successful backup command or a file existing on disk |

The earlier Research text strongly favors OIDC/BFF, a particular HTTPS topology and SSE for the first profile. Those are **well-motivated security and cost alternatives**, not separately authorized universal Product defaults. The selected remote deployment's identity and security owner must admit their exact policies. Independent native integration and fault tests determine the real compliance envelope; a source-located document, validated schema or successful GitHub documentation CI establishes only preparation.

**Cost and countercases:** supporting a second release train (host + client) requires versioned capability negotiation even with a project policy permitting breaking changes; compatibility recognition is not a promise to keep old Python APIs. A broker, container and full-text search are optional response to actual scale, retention and operator needs, not a prerequisite merely because the Web UI exists. A central host may improve multiuser sharing while introducing a larger blast radius and need for secrets, auth, upgrades, backup and support operations. One Windows repository vs two remains an unresolved operational comparison.

**Open independent proof:** verify the six source-to-Science meanings and earlier seventeen exposure claims with a separate qualified reviewer; test the accepted Web and Windows/AppDock variants with authentic deployed builds; measure auth/retention/cost under admitted policies; perform cold Science-only Research Amputation.
