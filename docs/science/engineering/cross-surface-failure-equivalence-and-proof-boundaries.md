# Shared failure mechanisms across data, machine interfaces, authority and observability

**Scientific question:** when several Strategy Box research themes describe the *same outward incident*, which causal claims can reuse one test fixture, and which require distinct independently observed evidence? **Status:** cross-theme producer reconciliation, with no accepted new Product Decision, no deployed host and no executed conformance test claimed.

## Convergence without false corroboration

The publication currently contains separate target negative-test matrices for security/visibility, machine/domain operation bindings, execution and diagnostics, and source input receipts. The same hypothetical lost network acknowledgement may legitimately appear in all four matrices because it threatens several different guarantees. Repeating a failure in four studies **is not four independent observations** and does not justify multiplying risk severity, assurance coverage or implemented feature count.

A reliable test distinguishes at least **domain-computation truth**, **command admission/permission**, **actual externally visible effect**, **durable application state**, **technical diagnostic observation**, **Artifact publication/availability**, and **third-party platform lifecycle/health**. Shared fixture reuse may reduce cost, but each distinct outcome claim needs its own oracle and target owner.

## Minimal end-to-end challenge without premature architecture

A bounded pilot can combine **two named but independently authenticated participants, two clients, one shared Work, a retained publisher input, a typed domain operation, one long-running Run, a safe file-writing Effect, a staged Artifact and one separate failed technical log sink**. Faults should be introduced **one at a time**, with stable Run/Attempt/source/target revisions, so correlation does not hide which authority failed. A future hosted pilot can add a network disconnect and an external platform problem-registering adapter only after those capabilities actually exist.

For each case collect an *oracle vector*, not merely a green UI state: `{trusted_actor, current_grants, operation_definition, binding_revision, input_receipt, planned_effect, observed_effect, run_status, artifact_status, diagnostic_status, platform_status}`, omitting unavailable fields rather than fabricating them. Treat explicit `UNKNOWN` and `BLOCKED_NOT_IMPLEMENTED` as meaningful bounded outcomes.

## Cost and opposite failure risks

The system should not allocate a dedicated microservice or database just because a semantic noun exists. One application host can implement several logical authorities; a self-contained local Python library continues to serve direct notebook callers with the OS privileges of their process. Conversely, collapsing every guarantee into a single optimistic `ok=True` flag would permit misleading source, permission, output and retry claims.

A single scripted fault may validate multiple invariants, but its test report must mark **which real channels actually ran**. For example a simulated FileStore exception is useful direct Python Current HOW characterization but is **not** an execution of remote-session ACL, live external problem recorder or deployed host recovery.
