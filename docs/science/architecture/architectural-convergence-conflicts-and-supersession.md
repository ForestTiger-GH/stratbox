# Architectural convergence, competing meanings and the cost of premature decisions

**Scope and status.** This article recovers the independent 2026-10-08 *Corpus Map & Open Questions* research (`SB-SRC-0048`, frozen blob `1f0c9592c63ac85aeac48fc8414378c4da334b73`, L1–L1509) as a bounded account of Strategy Box's competing conceptual models. It describes **why** several apparently conflicting proposals arose, what remains useful, which old directions were displaced, and the evidence needed to move from research convergence to product commitment. This is not an acceptance of an entire prior study, an audited count of all original research meaning, or a Product Decision.

The underlying historical map covered **27 dated second-branch investigations** and four historical notes as they existed on 2026-10-08. That number is **not** the complete current 566-identity consolidation census or evidence that those 27 sources have been independently re-read and losslessly certified in this cycle. Source reports of current code are dated observations, independently revisable by direct owner code and tests.

## 1. Why a mature research corpus can lack one ontology

Multiple investigations can converge on a needed **responsibility** while disagreeing about the name of its object, its persistence threshold or its future repository. A new name may describe a real distinction (Work versus a single execution Attempt), a redundant projection (Case card versus Run view), a deployment role (host process), or an unnecessary extra domain (AI-only operation stack).

The robust evaluation order is:

```text
what durable meaning or accepted behavior is at stake?
  → who has authority to change it?
  → what contract and verification witness is needed?
  → which current implementation supplies part of it?
  → does an independent package/process/repository add a demonstrated advantage?
```

This protects both source provenance and budget. Chronological recency alone does not prove a claim; observations of current code outrank target speculation **within their dated implementation scope**. Research agreement strengthens a hypothesis, but cannot create an installed service, a completed migration, a valid external permission or an approved organizational policy.

## 2. Seven interacting research families

The original 27-study map can be understood as seven overlapping evidence families, not seven service boundaries:

| Family | Main scientific question | Cross-family dependency |
| --- | --- | --- |
| **Current implementation baselines** | What do core and desktop actually expose and persist? | Prevent target concepts from being misreported as shipped. |
| **Sources, data and knowledge** | When do bytes become qualified observations, models, evidence and artifacts? | Evidence must be pinned into execution, acceptance and publication. |
| **Capability and execution** | Which operations, compositions, plans, retries and effects share an executor? | Depends on identity, state, authority and domain meaning. |
| **State and collaboration** | Who writes durable Work/Job/cursor truth, who sees it, and how does it recover? | Depends on permissions, retention, versioning and host profile. |
| **Clients and visual/report design** | Which semantics are portable across Windows, browser, Android and produced files? | Depends on stable application projections and separate style lifecycles. |
| **Neutral extensions and machine consumers** | How can installed components contribute a governed capability without bypassing public contracts? | Depends on curated operation registry, binding, readiness and effect gates. |
| **Cross-system integration** | What remains one product across core, application, platform and clients? | Must follow all six families, not dictate every repository at the outset. |

Per-study observations in the historical map are **routing/provenance**, not independent implementation proofs. Data-quality findings are reviewed against direct domain owner code; multiuser and mobile proposals against actual service/client maturity; user interface and report-style claims against their separate consumers; and public extension architecture against neutral contracts only. This prevents a map-of-research from being mistaken for a certification of each underlying investigation.

## 3. Ten original conflict classes, with different dispositions

| Corpus-map ID | Conflicting concepts | Evidence-sensitive disposition |
| --- | --- | --- |
| **C1** Command versus Operation | Low-level executable step versus curated semantic capability. Treat Command as optional technical term pending independent consumer; Operation has stronger public/domain use-case support. |
| **C2** Scenario versus Cascade versus Machine Scheme | User-offered workflow, larger composition and machine-readable reusable graph may overlap. Version/effect/consumer tests must determine distinct identities. |
| **C3** Work versus Case | Current Case is run-like; future Work outlives a single execution. Define whether Case adds separate owner/lifetime or only presentation. |
| **C4** Job versus Run | Different research used both for execution occurrence and claimable unit. One explicit model of admission, attempts and parent cardinalities is needed. |
| **C5** application library versus headless host | Stable logical application authority; process, reusable package and separate Git owner remain physical choices. |
| **C6** dedicated design repository | Common semantic visual language is useful; independent package/repository is conditional on real clients and releases. |
| **C7** product automation versus platform scheduler | Product owns due-event/business schedule meaning; deployment platform owns service/process primitives. |
| **C8** SQLite versus PostgreSQL | In original 2026-10-08 research, different local/server scopes, not a mutually exclusive universal answer; **later research also retains a file-first single-writer/journal alternative**, requiring a fresh storage decision for the actual profile. |
| **C9** Scenario-first navigation versus Thread/Work-first | Existing scenario chat is genuine current UI; durable multi-Work context suggests later human-centered Work navigation, pending product testing. |
| **C10** immediate content-addressed storage versus minimal design | Immutable output bytes can benefit from digest identity; a universal CAS service is not justified without artifact volume, retention and failure evidence. |

These are not ten identical `CONFLICT` states: C7 is a responsibility-level clarification; C8 often a deployment-scope distinction but has later additional alternatives; C6 and C10 lack proof of *physical* necessity; C1–C4 need stable object semantics. An updated conflict conclusion must retain this provenance rather than silently rewriting an old report.

The historical `Command/Operation` and `Scenario/Scheme/Cascade` investigations made useful execution-plan and typed-port proposals. Even if their names are simplified, their requirements for validity, input/output types, idempotency, cancellation, resource claims, side-effect fencing and compositional evidence remain potentially material. See [capability definitions](../capabilities/definitions-plans-and-execution-truth.md) and [composition alternatives](../capabilities/composition-identity-and-user-machine-projections.md).

## 4. What late evidence displaced—and what it did not

The source records **19 superseded/rejected table rows** of earlier directions. Their useful residues and caveats are important:

| Displaced direction | Retained usable meaning |
| --- | --- |
| Homemade launcher, GUI inside library | Easy activation remains a product need; platform installation and a separately reusable core are different owners. |
| Product scheduler entirely delegated to deployment platform | Platform scheduling may execute a timer; product still owns trigger interpretation, execution Work and audit. |
| Every domain Operation automatically becomes a user Scenario | User offers should be curated; one canonical operation can serve notebook, app and machine caller. |
| Background as Scenario domain subtype; separate background engine | Background is a policy/lifetime of the same governed execution model. |
| Qt thread as enduring Job authority; five desktop JSON files as shared truth | Current local prototypes exist; managed state needs independent writer, durable admission and recoverable outcomes. |
| Six equivalent primary navigation tabs; chat=Case=Scenario | Product navigation should reflect Work, evidence and actions rather than accidental current model names. |
| Physical output path, mtime or late `latest` lookup as authoritative identity | Stable snapshot and artifact IDs, effective revisions and lineage are separate. |
| Traceback/error string as product truth; timeout necessarily means failed effect | Typed result and UNKNOWN/reconciliation with protected diagnostics. |
| Generic unbounded retry or installed extension automatically active | Effect-aware idempotency and explicit provider selection/readiness. |
| Arbitrary UI widget injection, separate AI-only capability/execution stack | Bounded resource contributions and one governed capability/application authority across consumers. |
| Dedicated design repository already decided | Logical tokens and accessibility rules survive; packaging decision remains open. |

The terms *superseded*, *rejected alternative*, *implemented mismatch* and *unknown* are deliberately different. An old implementation can still exist and require retirement; a rejected architecture can contain reusable requirements; an unbuilt target can be scientifically plausible without release admission.

## 7. Eight dated current-code gaps, distinct from architecture hypotheses

The 2026-10-08 map recorded these implementation risks from existing source-owner reviews:

1. Core package `0.8.0` versus Windows dependency/manifest pin `0.2.1`: a static compatibility concern, requiring a fresh install test.
2. Windows manifest contract version and README/test expectations disagree: a documentation/test alignment issue, not a witnessed installation failure.
3. Generic public boundaries require hygiene inspection of existing packaging/metadata; this article discloses no deployment-specific internals.
4. Generated/temporary files present in the dated Windows repository snapshot: repository hygiene, requiring direct current-tree recheck before cleanup.
5. Uneven test coverage and CI/release automation: a proposed assurance improvement, not proof all uncovered code is broken.
6. Packaged registries and reference snapshots lack one proven freshness/admission lifecycle: a reproducibility concern.
7. Some file/data APIs conflate missing, wrong-type and empty outcomes; a statement about one specific method is **not** proof all arbitrary backend failures are swallowed.
8. UI projections for background work, presence and assignments exceed the certified state of their underlying shared execution services.

These are **time-pinned findings**; no current code changes or runtime remediation are performed by the knowledge consolidation. The distinction matters especially for not mistaking a current GUI label for durable multi-user functionality.

## 8. How to decide without losing historical meaning

For each contested object or physical component, preserve the original question, source/date, viable alternatives, evidence threshold and **rejected with reason** options. A typed `UNKNOWN` is a legitimate resolution when the decisive user workflow or installed test is absent. A term should become a first-class stored entity when separate identity, access, lifecycle, audit and consumer needs demand it; otherwise a field or projection may suffice. A repository should be extracted for independent evolution or trust—not on diagram aesthetics.

The strongest next vertical slice is one business calculation with pinned source/registry definitions, two invocation contexts, one authorized application Run, an explicit effect/artifact receipt, and a reconnect/lost-confirmation test. This may resolve multiple C1–C10 distinctions without inventing new services. Future Science admission additionally requires **bidirectional** verification: every material original claim is accounted for or explicitly excluded, and every public Science claim has sufficient direct support. This document itself is only provisional producer-level conservation.
