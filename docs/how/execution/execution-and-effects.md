# Исполнение и эффекты — HOW-R

**Target HOW:** `TH-SB-2026-10-09-CANDIDATE-1` (непринятый механизм).  
**Область:** один аналитический запуск и его последствия; shared-node/remote расширения применимы только после утверждения соответствующего профиля.  
**Связанные предложения WHAT:** `TW-C01` (достоверность отсутствия данных), `TW-C02` (статусы), `TW-C03` (отмена), `TW-C04` (повтор), `TW-C06` (артефакты).

## Реализационные роли

1. **Core Operation**: валидирует предметный запрос и выполняет банковско-макроэкономическую операцию; возвращает значения с предметной квалификацией и типизированные диагностические признаки. Его алгоритм не зависит от конкретного UI.
2. **Application execution authority** (*candidate logical unit*): допускает вызов, связывает его с субъектом и effective permissions, сохраняет логическую идентичность/решения о запуске, определяет lifecycle state и учитывает побочные эффекты. Пока выбор процесса, пакета, службы и репозитория открыт.
3. **Executor adapter** (*candidate*): исполняет техническую попытку на разрешённом вычислительном ресурсе, передаёт прогресс и возвращает проверяемые receipts. Наличие адаптера не даёт ему полномочия принимать бизнес-результат.
4. **Surface**: отправляет команду и показывает состояния и артефакты, но в управляемом многопользовательском профиле не является единственным источником долговременной истины.
5. **Platform boundary**: передаёт доступный согласно своей версии контекст окружения и управляет собственным жизненным циклом узла. Платформенная готовность означает готовность окружения, а не доказанную правильность банковского расчёта.

## Предлагаемые отношения identity

`OperationDefinition` задаёт вид операции. `OperationBinding` закрепляет его за версией кода, ресурсом, разрешениями и профилем. `Invocation` обозначает запрос пользователя или автоматики. `Run` — логическое выполнение; `Job` — планируемая единица; `Attempt` — конкретный исполнительный заход. `EffectReceipt` описывает подтверждённый побочный эффект. Это отдельные identity, связь через stable references и versioned request digest; **точные сериализованные поля и сроки хранения требуют Product Decision**.

## Состояния и наблюдаемая семантика

Для Job предлагается независимая ось планирования `ADMITTED/WAITING/RUNNING/TERMINAL`, ось исхода `SUCCEEDED/FAILED/CANCELLED/PARTIAL/OUTCOME_UNKNOWN` и ось внимания `NONE/WARNING/NEEDS_REVIEW`. Набор словарей **иллюстративен, не действующий API**. Один terminal record следует фиксировать через compare-and-transition на authority-стороне, но последующее доказательство внешнего эффекта может пополнять reconciliation evidence, не переписывая историю прежнего наблюдения.

| Событие | Допустимое трактование | Что запрещено обещать |
| --- | --- | --- |
| Аналитический код вернул валидный результат | Core operation завершила вычисление в указанном scope | Что результат принят пользователем или источник актуален без проверки |
| Запрос на отмену зарегистрирован | Cancellation requested | Что физический процесс остановлен до эффекта |
| Локальный timeout после внешнего обращения | Ответ не получен | Что внешняя запись/удаление точно не произошло |
| Прерванная публикация файла | Bytes могут оставаться в staging | Что артефакт завершён и доступен |
| Ошибка источника | Domain failure или uncertain source status | Что официальный источник вообще не содержит данных |

## Приём, дублирование, выполнение

- Команда admission проверяет principal, доступность capability, request schema, ресурсы и оценённые эффекты.
- Для effectful операции идентичные `invocation_key + digest + scope` желательно связывать с тем же logical execution. Изменение digest при прежнем ключе отклоняется как конфликт. **Гарантия и окно действия ключа пока открыты.**
- Retry допускается лишь когда failure class и данные о предыдущем эффекте разрешают новую попытку; особенно опасны изменения файлов, сетевой side effect и уничтожение данных.
- Планируемый cancel требует cooperative checkpoints до irreversible commit и явного результата, если effect уже мог произойти.
- Продуктовые события и технические логи могут описывать один запуск, но выполняют разные функции; log line не определяет состояние Job.

## Конкретный сценарий аналитики

Аналитик выбирает обновление данных регулятора или экспорт истории эскроу. Frontend собирает параметры, application authority (*если принята*) валидирует место вывода/полномочия, исполнение вызывает каноническую core operation, затем сохраняет result provenance и передаёт артефакт в проверенную публикацию. Успех пользовательского просмотра требует отдельного подтверждения готовности артефакта. Текущий Windows-сценарий лишь последовательный run с локальной историей: **описанная здесь долговременная authority ещё не существует как подтверждённый сервис**.

## Выборы и остаточная свобода

| Решение | Статус | Ограничение |
| --- | --- | --- |
| Самостоятельный headless core | FIXED boundary | UI и managed launcher не становятся доменными зависимостями |
| Единый канонический execution owner | UNRESOLVED_BLOCKING | Нужен Product Decision `SB-Q-01` о lifetime и supported profiles |
| Физическая структура Job storage | UNRESOLVED_BLOCKING | `SB-Q-02`: guarantees, data retention и recovery |
| Разделение execution identity и transient worker attempt | BOUNDED_OPEN candidate | Возможна иная схема при той же требуемой наблюдаемой семантике |
| Retry/idempotency/approval policy | UNRESOLVED_BLOCKING | `SB-Q-03/04`: risk classes, exact authorization |
| Технология очереди, СУБД, процессная граница | BOUNDED_OPEN | Пока альтернативы не могут быть сузены без профиля и измерений |

**Reopen:** изменённые Product commitments, протокол внешнего managed runtime, наблюдаемый новый executor, подтверждённый effect incident или fault-injection результат. Без снятия blocking choices этот кандидат не является пригодной к непосредственной production-реализации спецификацией.
